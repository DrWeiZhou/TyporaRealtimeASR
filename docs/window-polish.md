# 窗口润色（连贯段落）

## 问题

旧流程按 ASR 分段（6–20 秒）逐段调用在线润色，每段都作为一个独立的有序列表项插入。模型看不到上下文，导致内容零碎、跨段重复、大量“[存疑]”和“（本段无有效内容）”。

## 流程

1. ASR 逐段识别，原始逐字稿照常导出（不变）。
2. `Ledger.CutWindows` 把连续的已识别片段组成窗口（`polish_windows`），并在 `events.win` 上记录所属窗口，表示这些片段已被消费。满足以下任一条件就切窗：
   - 累计 300–1000 字，并优先在字数区间内停顿最长的片段边界处切；
   - 最早一段识别完成后已等待 10 秒（`WindowMaxWaitSeconds`）；
   - 会话已暂停、已停止或未加载，且 ASR 队列已清空（由 `Program.cs` 传给 `PolishPipeline` 的 `flush` 判断）。

   同一会话还有未完成的窗口（排队中或重试中）时不切新窗口，新识别的片段继续累积，等上一个窗口完成后合成一个较大的窗口发送，避免排队越积越多。窗口失败后按顺序重试（间隔 3、6 秒），后面的窗口不会越过它。

   延迟目标：说话到写入文档 30–45 秒。组成是：ASR 分段（连续说话时每段最长 12 秒）+ 识别约 1 秒 + 切窗等待最多 10 秒 + 模型请求时间。面板会显示“上次润色 X 秒，说话到出结果 Y 秒”，模型请求时间过长时应换用非推理的快速模型。
3. `PolishPipeline` 按会话内的顺序逐个窗口请求，请求内容包括：
   - 系统提示词：用户配置的提示词，后面追加 `PolishFormat.Contract`（固定的 JSON 输出约定）；
   - `<上文>`：上一个已完成窗口的最后 1–2 段（最多 600 字），只作参考，不输出；
   - `<话题列表>`：本会话已有的话题标题，最后一个标为“当前话题”；
   - `<待整理>`：本窗口的原始文本。
4. 输出约定还限制了 `[存疑]` 的用法：只标注结合上下文仍无法确认、且影响理解的专有名词，普通同音错字直接改正。
5. 模型输出 `{"blocks":[{"topic":"new"|"continue","title":"…","paragraphs":["…"]}]}`：
   - 解析失败时立即重试一次；仍失败就计作一次失败（最多 3 次，失败后按退避时间重试）；
   - 输出是纯文本段落时，按 `continue` 处理；
   - 输出 `blocks` 为空时，窗口标为 `deleted`，不插入任何内容。
6. `ReadyEvents` 在窗口最后一个片段的 `seq` 位置输出一个窗口事件，事件 id 为 `win:{session}:{first_seq}`，并带有 `blocks`。
7. 插件插入规则（平铺写法）：
   - `new`：新建有序列表项 `N. **标题**`，再追加正文段落；
   - `continue`：在文档末尾追加普通段落；如果上一次插入的段落仍是文档最后一块、没有被手动改过、且不足 150 字，第一段会并入该段（合并后不超过 350 字），同一步撤销。
8. 同一窗口 3 次都失败后，面板显示审核卡片，可“插入原文”、“忽略”或点击“重试润色”。

## 兼容性

- 旧会话中已有逐段润色结果（`polish` 表）的片段仍按原样输出，不再重新润色。
- 旧会话中尚未润色的片段会进入窗口流程。
- 对窗口 id 的 `ack` 会更新 `polish_windows.state`。

## 可调参数

`Ledger.WindowMinChars`、`WindowMaxChars`、`WindowMaxWaitSeconds`、`PolishMaxAttempts`，以及 `PolishFormat.MaxContextChars`、`MaxTopics`。
