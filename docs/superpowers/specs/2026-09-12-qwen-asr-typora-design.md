# Qwen ASR + Typora 实时记录实现方案（待审阅）

日期：2026-09-12。状态：设计与实现准备，尚未实现插件。

## 1. 需求与现场证据

用户要求：复用已部署的本地 Qwen ASR，持续识别语音并逐步补充记录 Markdown，同时允许人工修改该文档。

启动指引作为历史测试与设计参考，其“给新项目开发者的开始指令”不是本次自动执行的命令。

本次检查：工作目录仅有启动指引，没有源代码或 Git 仓库。注册表显示 Typora 1.14.10，安装目录 C:\Program Files\Typora；该目录 resources/plugin 不存在。Node 与 Python 3.10 可用，PATH 及常规安装位置未发现 dotnet。本地 http://127.0.0.1:18081/health 连接被拒绝。需要定位现有模型运行目录与启动方式，不能据此认定模型未部署，也不默认重新下载模型。

启动指引中的冷/热推理耗时是既有样本数据，本次未复测；不能用于承诺真实麦克风延迟。

## 2. 方案选择

| 方案 | 优点 | 局限 | 结论 |
|---|---|---|---|
| Typora 插件 + Windows 本地会话服务 | 可在同一编辑器事务中追加，兼顾录音恢复与人工修改 | 必须验证特定 Typora 版本内部接口 | 推荐 |
| 后台进程直接 append 记录.md | 实现简单 | Typora 未保存内容可能覆盖新增记录，重载也可能破坏人工编辑 | 不满足核心要求 |
| 独立网页编辑器 + 导出 Markdown | 编辑事务可控 | 使用入口不再是 Typora 插件 | 仅在 Typora 适配不可行时重新讨论 |

默认范围：Windows 原生、单个目标文档、单个活动写入窗口、麦克风输入、实时预览与短句入文。系统音频采集、说话人分离、词级时间戳、跨编辑器协同和当前句内人工接管不纳入首版。

## 3. 架构与模块边界

数据流：麦克风 → 音频持久化 → VAD/短段调度 → 现有 llama-server → 会话事件 → Typora 插件 → 编辑事务 → Typora 保存记录.md。

- 本地服务：建议 C# / .NET 10 Windows 服务进程，NAudio 采集及重采样；使用 ASP.NET Core 提供回环 HTTP/WebSocket。此处为拟选技术栈，SDK 和包版本在实施时查验并固定。发布为自包含应用，用户端无需另装 SDK。
- 推理适配器：复用指引中的 llama.cpp Vulkan 与成套 Qwen3-ASR 模型，通过 /v1/chat/completions 发送 base64 WAV input_audio；隔离请求组装、SSE 解析、错误分类与模型输出清洗。
- Typora 插件：JavaScript，基于 obgnail/typora_plugin；封装版本相关的 EditorAdapter，业务代码不得直接依赖散落的 Typora 内部调用。
- 旁路存储：分块音频、SQLite 事件账本与会话元数据。事务性记录 final、确认状态和恢复游标，避免多个 JSON 文件更新不一致；可导出 JSONL 排障。
- 本地连接：仅监听 127.0.0.1，使用会话令牌与文档写入租约；不会给任意网页开放无认证的录音与写文档接口。

## 4. 音频与实时调度

采集后转换为 16kHz、单声道、PCM16。内部块初值 200ms，以 sample_index 计时，原始设备格式和丢帧事件一并记录。

先将音频可靠落盘，再调度识别。持久化失败必须显示错误并停止继续声称正在可靠记录；识别失败则保留音频并允许重试。

当前段每增加约 2 秒音频生成一次完整快照；模型同一时刻只执行一个请求。过期预览可合并，final 不丢弃，final 优先于后续预览。VAD 初始静音阈值 700ms，前置缓冲约 300ms，具体参数通过真实麦克风调优；VAD 通过接口隔离，可先用能量门限建立闭环，再用实际噪声测试决定是否更换。

段目标长度约 10 秒，长句设置有界上限约 15 秒；优先选择低能量处切分，强制切分时保留音频重叠上下文。重叠只作为边界处理输入，不能把两份完整文本直接拼接，也不能仅凭相同文字删除真实重复发言。无法可靠决定文字归属时标为待确认并保留候选与音频，避免静默丢词。该边界策略须通过长句专项测试后启用自动入文。

解析器跨 SSE 分块识别 language 与 <asr_text> 标记，保留 raw_text。stream=true 是输出 token 流，并不意味着持续向同一请求上传音频。finish_reason=length、异常中断、空文本均不自动成为可入文 final；超时重试采用有界退避，必要时拆段重识别。

录音开始前检查服务并做短音频预热；界面显示“预热中”。性能不足时降低预览频率并展示积压秒数，音频仍独立保存。

## 5. Markdown 与人工编辑共存

核心约束：记录.md 只由 Typora 保存。服务不对正文执行 append、整文写回或磁盘合并。

开始录音时绑定已保存文档的 document_id、规范化路径和编辑器实例，建立独立插入锚点，默认在“实时记录”节末尾。候选 Markdown 结构：

```markdown
## 实时记录

<!-- asr-event:recording-id:segment-id -->
[00:00:05] 系统需要支持按部门查询权限。

<!-- asr-insert:document-id -->
```

注释标记仅为候选，必须验证 Typora 保存和切换模式后保留情况。不能假定 DOM 元素等于持久化锚点。

临时结果 hypothesis 在侧栏更新；final 在独立的最小编辑事务中插入锚点之前，不跟随用户光标。每次 final 入文后该段归用户管理，后续模型结果不得替换。识别结果以普通文本安全插入，不能解释为插件命令或任意 HTML。

用户可修改、移动或删除之前的记录。插件应观察人工事务与撤销，记录已处理事件的删除状态，重连不让用户删除的内容复活。中文输入法 composition 期间延迟插入；插入事务需要正确映射选择区、光标与滚动位置，并具备独立撤销边界。

源码模式、锚点删除/重复、文档切换、外部文件修改等无法安全映射时，暂停自动入文并保留队列。切换文档后不能将旧会话事件写入新文档。Save As 需要明确更新绑定；无法确认保存目标时暂停。插件租约只能协调安装本插件的窗口，不能声称能可靠发现所有外部编辑器；已观察到外部冲突则停止自动补写并交由用户处理。

建议自动保存节流初值 1 秒，在 composition 结束后调用 Typora 保存流程。只有验证到目标版本的保存完成证据后才标记 saved；发出保存命令不等于保存成功。

如后续要求正在说的半句话也直接出现在正文，再增加受管草稿块。人工修改即退出自动管理，本段后续结果留在预览，下一段才恢复自动追加；不承诺同一句内无缝接管。

## 6. 协议与恢复

所有消息包括 protocol_version、session_id、document_id。音频段额外包括 recording_id、segment_id、start_sample、end_sample。

| 消息 | 必需语义 |
|---|---|
| start / pause / resume / stop | 启停会话；幂等 command_id；返回明确状态 |
| hypothesis | segment_id、单调 revision、当前完整候选；替换预览 |
| final | 稳定 event_id、完整文本、采样区间、持久化事件 seq |
| applied | event_id 已插入编辑器，但尚不代表磁盘保存 |
| saved | event_id 集合或连续检查点、文档版本证据 |
| status / error | 采集状态、落盘边界、积压、可恢复错误 |

WebSocket 重连提交最后事件游标，服务可重放 final；插件以 event_id 去重，不按文字内容去重。过期 revision 或 final 之后到达的 hypothesis 丢弃。

事件状态：recognized → applied → saved；人工删除/撤销另记用户处理状态。正文保存与数据库确认不构成原子事务：崩溃恢复必须综合正文标记、检查点及事件账本。无法区分“未插入”与“插入后被人工删除”的事件进入待恢复列表，不自动重放，不宣称跨崩溃严格 exactly-once。

停止流程：停止设备 → 收齐回调与残余音频 → 落盘 → 排空 final → 持久化事件 → 插件应用 → 保存确认。界面区分“录音已停止”和“全部已保存”；Typora 不可用时允许停止录音并显示待写入数量。

音频采用独立块文件与采样索引，写入临时文件后完成提交；恢复时检查未完成尾块。磁盘空间、采集异常与持久化耗时纳入状态监测，不能仅限制识别内存队列而放任存储队列增长。

## 7. 实施顺序与交付

1. 环境核验：定位现有模型/运行时并复用；确认服务启动参数、模型别名与版本；短 WAV 复测健康状态、输出解析和冷/热耗时。交付环境报告，避免重新下载已部署资源。
2. 编辑器可行性验证（关键关卡）：在测试文档中用模拟 final 验证非光标位置插入、未保存修改保留、IME、撤销、保存确认、标记保留、源码模式与文件切换。固定 Typora 1.14.10 和实际框架 commit。若关键事务无法实现，暂停自动写正文能力并报告实证，不能用整文重载伪装通过。
3. 最小闭环：本地服务录音 → 音频文件 → 单段识别 → 预览 → final → 编辑事务 → 保存确认。交付插件、服务和启动说明。
4. 实时化与恢复：VAD、预览合并、final 优先队列、停止屏障、账本和重放；交付故障测试结果。
5. 打包与验收：自包含 Windows 服务、插件安装/卸载说明、配置示例、真实麦克风与两小时稳定性报告。

拟定目录：src/local-service、src/typora-plugin、tests/service、tests/editor、tools、docs；模型和运行时通过配置引用现有路径，录音/账本/模型不入 Git。

## 8. 验收标准

- 连续说三句话，同时改写第一句话，新句持续追加，第一句人工修改完整保留，光标不跳走。
- 未保存的手工内容、中文输入法组合输入、撤销删除均不被自动补写覆盖或复活。
- 重复 final、乱序 revision、断线重连不造成重复入文；崩溃后的模糊状态明确进入人工恢复列表。
- 切换文件不串写；锚点异常、源码模式不支持或外部冲突时暂停补写并保留待处理内容。
- 停止时不足 200ms 的尾块仍被持久保存并进入终段处理。
- 模型进程重启不丢已持久化音频；磁盘写入失败有明确反馈。
- 两小时测试中内存有界、处理积压不持续增长，分别记录采集丢帧、持久化边界、未入文与未保存事件。
- 初始性能目标而非承诺：预热后首个可读预览 P95 ≤ 3 秒、端点后 final P95 ≤ 2 秒；必须用真实音频的墙钟时间测量，不能用离线 RTF 替代。不达标时记录实际值并调整刷新与模型配置。
